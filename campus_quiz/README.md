# campus_quiz

A campus events app built with **Flutter** (frontend) and **Serverpod**
(backend) on **PostgreSQL**.

The repository is a Dart pub workspace with three packages:

| Package              | Description                                                     |
| -------------------- | --------------------------------------------------------------- |
| `campus_quiz_server` | The Serverpod backend: models, endpoints, auth and migrations.   |
| `campus_quiz_client` | The generated Serverpod client. Regenerated by `serverpod generate`; never edit it by hand. |
| `campus_quiz_flutter`| The Flutter app.                                                   |

## Current state

The backend foundation for the campus events feature is implemented. The
Flutter app still contains the Serverpod starter demo screens (a greeting
demo and a sign-in demo); the product screens are not built yet.

Backend functionality that exists today:

- **Events feed** — browse events with start time, location, organizer,
  category and capacity, plus live RSVP counts.
- **RSVPs** — signed-in users can mark themselves as `going` or `interested`,
  change their status, and cancel. One RSVP per user and event, enforced by a
  unique index.
- **Authentication** — anonymous accounts (one tap, no registration) and
  email/password accounts. Either kind of account can RSVP.
- **Seeded content** — the development database is filled with sample events on
  the first server start, so the app always has content to show.

## Requirements

- Dart SDK `^3.12.2` (bundled with Flutter)
- Flutter `^3.44.4` (the pub workspace resolves all three packages, so Flutter
  is required even for backend work)
- Serverpod CLI `4.0.4` (must match the `serverpod` package version)

## Setup on Windows

```sh
# 1. Install the Serverpod CLI (matches the serverpod package version).
dart pub global activate serverpod_cli 4.0.4

# 2. Fetch the dependencies for the whole workspace.
cd campus_quiz
flutter pub get
```

Make sure `flutter` and the pub global bin directory
(`%LOCALAPPDATA%\Pub\Cache\bin`, or `%LOCALAPPDATA%\Dart\install\bin` if the
CLI was installed with `dart install`) are on your `PATH`.

### Environment variables

No environment variable is required for local development, but the server and
the tests **do need a passwords file**. Create
`campus_quiz_server/config/passwords.yaml` (it is gitignored, so it never
leaves your machine) with at least these keys:

```yaml
development:
  database: '<a random string>'
  redis: '<a random string>'
  serviceSecret: '<a random string>'
  jwtRefreshTokenHashPepper: '<a random string>'
  jwtHmacSha512PrivateKey: '<a random string>'
  serverSideSessionKeyHashPepper: '<a random string>'
  emailSecretHashPepper: '<a random string>'

test:
  database: '<the same value as above>'
  # ...the same keys as above
```

Generate the values with `openssl rand -hex 32`. Without this file the server
stops with `Missing password for "database"` and the test runner exits
silently with code 1.

The same values can be supplied through environment variables instead of the
file, using the `SERVERPOD_PASSWORD_<key>` naming, for example
`SERVERPOD_PASSWORD_database`. The CI workflow uses that form.

`config/passwords.yaml` and the embedded database data directory
(`campus_quiz_server/.serverpod/`) are gitignored. Never commit them.

### Argon2 and Windows application control

The sign-in flows hash secrets with Argon2, which loads a native library
(`serverpod_argon2.dll`). Some Windows machines block that DLL with an
Application Control policy (error 4551: *"An Application Control policy has
blocked this file"*), which makes every sign-in call fail while the rest of
the server works.

If that happens, build the server as a native executable, which links the
library into the binary instead of loading it from `.dart_tool`:

```sh
cd campus_quiz/campus_quiz_server
dart build cli
./build/cli/windows_x64/bundle/bin/main.exe
```

Note that the binary is started directly, so it does **not** apply pending
migrations. Run `serverpod start` once before it, or apply the migrations
yourself, so the database matches the models.

## Running the backend

```sh
cd campus_quiz/campus_quiz_server
serverpod start
```

`serverpod start` watches for file changes and regenerates code and applies
pending migrations on every restart. The servers are:

| Server       | Port | Purpose                                |
| ------------ | ---- | -------------------------------------- |
| API server   | 8080 | The endpoint API the app talks to.     |
| Insights     | 8081 | Serverpod Insights (optional).         |
| Web server   | 8082 | Serves the Flutter web build at `/app`.|

### The database

There is no separate database to install. Both the development and test
configs set `database.dataPath`, so Serverpod runs an **embedded
PostgreSQL** instance and manages it for you:

- The PostgreSQL bundle (PostgreSQL + PostGIS + pgvector) is downloaded from
  GitHub Releases on the first run and cached in
  `%LOCALAPPDATA%\serverpod\Cache\pg-binaries`. Later runs start in about a
  second.
- PostgreSQL **refuses to run from an elevated (Administrator) terminal**.
  Run the server and the tests from a normal, non-elevated terminal.
- The database listens on a loopback TCP port. The password is taken from
  `config/passwords.yaml`.
- `docker-compose.yaml` is **not** used for local development or tests. It is
  kept for manual setups against a containerised PostgreSQL.

To inspect the database with an external tool, run `serverpod database start`
in the server package; it prints a connection URI.

### The Flutter app

The app is started together with the server by `serverpod start` (see
`flutter_apps` in `campus_quiz_server/pubspec.yaml`). To run it separately:

```sh
cd campus_quiz/campus_quiz_flutter
flutter run -d chrome --dart-define=SERVER_URL=http://localhost:8080
```

On a physical device, replace `localhost` with the LAN IP of your machine.

## API overview

All endpoints live in the `events` endpoint (`client.events.*` on the client
side). Reading is public; RSVP endpoints require a signed-in user.

| Method         | Parameters                                | Returns              | Auth |
| -------------- | ----------------------------------------- | -------------------- | ---- |
| `listEvents`   | `category?`, `upcomingOnly?`, `limit?`     | `List<EventSummary>` | No   |
| `getEvent`     | `eventId`                                 | `EventSummary`       | No   |
| `rsvp`         | `eventId`, `status?` (`going`/`interested`)| `Rsvp`               | Yes  |
| `cancelRsvp`   | `eventId`                                 | `void`               | Yes  |
| `myRsvps`      | —                                         | `List<Rsvp>`         | Yes  |

`upcomingOnly` defaults to `true`, `limit` to 50 (clamped to 1..100) and
`status` to `going`.

Over HTTP the path format is `/<endpoint>/<method>`, and parameters are sent
as a JSON body (POST) or as query parameters:

```sh
# List the upcoming events.
curl http://localhost:8080/events/listEvents

# List the tech events only.
curl -X POST http://localhost:8080/events/listEvents \
  -H 'Content-Type: application/json' \
  -d '{"category":"tech","upcomingOnly":true,"limit":10}'

# Sign in as a guest and RSVP to an event.
TOKEN=$(curl -s -X POST http://localhost:8080/anonymousIdp/login \
  -H 'Content-Type: application/json' -d '{}' | sed -n 's/.*"token":"\([^"]*\)".*/\1/p')

curl -X POST http://localhost:8080/events/rsvp \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"eventId":"<event-id>"}'
```

Failures are reported as an `EventException` with a machine-readable `code`:

| Code                    | Meaning                                        |
| ----------------------- | ---------------------------------------------- |
| `UNAUTHENTICATED`       | The endpoint needs a signed-in user.           |
| `EVENT_NOT_FOUND`       | No event with that id.                         |
| `EVENT_ENDED`           | The event has already ended.                   |
| `EVENT_CAPACITY_REACHED`| The event is full.                             |
| `EVENT_INVALID_CATEGORY`| The category is not one of the known categories.|
| `RSVP_INVALID_STATUS`   | The status is not `going` or `interested`.     |

## Working on the backend

After changing a model (`*.spy.yaml`) or an endpoint, regenerate the code and
the client:

```sh
cd campus_quiz/campus_quiz_server
serverpod generate
```

After changing a model that has a table, create a migration:

```sh
serverpod create-migration
```

Review the generated `definition.sql` and `migration.sql` before committing
them.

## Tests

```sh
cd campus_quiz/campus_quiz_server
dart test
```

The tests start their own embedded PostgreSQL instance, so no Docker and no
running server is needed. The same commands the CI runs are:

```sh
dart analyze --fatal-infos
dart format --set-exit-if-changed .
dart test
```
